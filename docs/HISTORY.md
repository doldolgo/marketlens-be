# 김프/역프 기록 시스템 (기록/통계 창)

김프/역프가 "언제, 얼마 만에, 얼마로" 바뀌었는지를 기록해 두는 시스템이다.
실시간 스프레드 창이 `market_snapshots`(현재 상태)를 쓴다면, 기록/통계 창은
`premium_archive`(누적 기록)를 쓴다.

저장 구조는 [DB.md](DB.md), 엔드포인트 상세는 [API.md](API.md) 참고.

## 어떻게 쌓이나 — 두 경로

**① 실시간 (POST /refresh, 1분 cron)**
refresh 가 market_snapshots 를 갱신한 직후, (국내 거래소 × 국내·해외 동시
상장 코인)마다 김프/역프를 계산해 아카이브에 한 줄씩 추가한다.
체결측 호가 기준이라 /spreads 화면과 같은 값이다. 페어: 업비트×바이낸스,
빗썸×바이낸스.

**② 대량 채우기 (scripts/bulk_archive.py)**
아카이브 타임라인의 **가장 처음/가장 마지막 시각**을 읽고, 그 밖의 구간
(목표 시작 ~ 첫 기록, 마지막 기록 ~ 지금)을 플랫폼이 지원하는 최소 간격으로
한 번에 계산해 채운다:

| 재료 | 원천 | 간격 |
|---|---|---|
| 국내 가격 | 업비트 초봉 (보관 3개월 롤링) | 체결 있던 초 |
| 해외 가격 | 바이낸스 1초봉 (전체 이력) | 매초 |
| 환율 | 업비트 KRW-USDT 분봉 종가 (`--usdkrw-pace` 로 요청 간격 조절) | 1분 |

세 값 중 하나라도 변한 초마다 김프를 다시 계산해 한 줄 만든다 (forward-fill
병합). 캔들에는 호가가 없어 **종가 기준**이다 — 실시간 기록(호가 기준)과
계산 기준이 다르다는 점만 기억하면 된다.
대상 페어는 업비트×바이낸스다 (빗썸은 초봉 API 가 없어 대량 채우기 불가 —
빗썸 페어는 실시간 기록으로만 쌓인다).

## 조회 API

### GET /history/premium — 김프/역프 기록

```
GET /history/premium?base=BTC&unit=week&date=2026-08-14&limit=20
```

| 파라미터 | 의미 |
|---|---|
| `base` (필수) | 코인 심볼 (BTC) |
| `unit` (필수) | `week`(ISO 주: 월~월) 또는 `month`(달력 월) |
| `dom` / `fx` | 페어 선택 (기본 upbit / binance) |
| `date` | 구간을 고를 기준 날짜 — 그 날짜가 **속한** 주/월. 생략 시 오늘 |
| `offset` / `limit` | 페이지네이션 (기본 10,000, 최대 50,000) |

응답 골격:

```jsonc
{
  "dom": "upbit", "fx": "binance", "base": "BTC",
  "unit": "week", "start": "2026-08-10T00:00:00+00:00", "end": "...",
  "first_ts": 1786665603,      // 첫 기록의 절대 시각 (epoch 초)
  "count": 38210, "returned": 20, "has_more": true,
  "summary": { "first_fwd": 0.50, "last_fwd": 0.44, "min_fwd": ..., "max_fwd": ... },
  "events": [
    { "dt": 0, "fwd": 0.50, "rev": -0.55 },   // 기준점
    { "dt": 5, "fwd": 0.62, "rev": -0.67 },   // 5초 뒤 김프 +0.62%로
    { "dt": 7, "fwd": 0.44, "rev": -0.49 }    // 다시 7초 뒤 +0.44%로
  ]
}
```

DB 는 절대 시각(epoch 초)으로 저장하고 응답은 **직전 기록과의 시간 차(dt)**
로 준다 — `first_ts` 에 dt 를 누적하면 절대 타임라인이 복원된다. dt 는 항상
전체 열 기준이라 페이지를 이어 붙이면 완전한 로그가 된다.

### GET /history/status — 플랫폼 상태·입출금 실패율

플랫폼당 한 행: 마지막 수신 시각, 상장 마켓 수(현물/선물), 입출금 실패
횟수/전체 업데이트 횟수, 그리고 계산된 `dw_fail_rate` (실패율 0~1).

## 대량 채우기 실행법 (최초 1회 + 필요할 때)

```bash
python -m scripts.bulk_archive --bases BTC
```

| 옵션 | 의미 |
|---|---|
| `--bases BTC,ETH` | 채울 코인 (쉼표 구분) |
| `--days 92` | 목표 구간 (기본 92일 — 업비트 초봉 보관 한계) |
| `--usdkrw-pace N` | 환율(KRW-USDT 분봉) 요청 간격 초 — 업비트 한도를 초봉과 나눠 쓴다 |
| `--pace-*` | 요청 간격 조절 |

- **하루 단위로 커밋 + 같은 시각 재삽입 무시**라 중단 후 재실행에 안전하다.
- 소요: 코인당 업비트 ~20분 + 바이낸스 ~15분 + 환율(stride 30) ~10분.
- 업비트 초봉은 3개월 롤링 — **미룰수록 과거를 잃는다.** 배포 후 바로 한 번 돌릴 것.
- 업비트 레이트리밋(10 req/s)은 라이브 refresh 와 공유되므로 기본 pace 유지.

## 운영

별도 cron 이 필요 없다 — **refresh 가 돌면 기록도 같이 쌓인다.**
아카이브 후미가 비는 경우(서버 중단 등)엔 bulk_archive 를 다시 돌리면
마지막 기록 이후 구간이 채워진다.

## 알아둘 것

- 실시간 기록은 refresh 주기(1분) 간격, 대량 채우기는 초 단위 간격이다 —
  한 타임라인에 두 해상도가 섞이는 게 정상이다.
- 실시간은 호가 기준(체결 가능 가격), 대량은 종가 기준이라 같은 시각이어도
  약간 다를 수 있다 (스프레드만큼 실시간 쪽이 보수적).
- 환율의 원천 해상도는 은행 고시(평균 ~44초)다 — 그 이하의 "초당 실환율"은
  존재하지 않는다.
