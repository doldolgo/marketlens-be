# MarketLens 구현 체크리스트

목업(**트레이딩룸** 대시보드)을 채우기 위한 작업을 **난이도 순 · 체크박스**로 정리했다.

- 대상: 탭 6개 · **8개 거래소 · 24개 코인 · 176 페어 · 실시간 갱신**
- 현재: 2개 거래소 · 코인 1개씩 요청 · REST 폴링

| 단계 | 내용 | 난이도 | 선행 | 진행 |
|---|---|:---:|---|:---:|
| 0 | 기반 구조 | — | — | ✅ 완료 |
| 1 | 거래소 커넥터 6곳 추가 | ⭐ | — | 🟡 빗썸 완료 |
| 2 | 국내 복수 지원 · 역프 | ⭐⭐ | 1 | 🟡 대부분 |
| 3 | 마켓 목록 · 페어 산출 | ⭐⭐ | 1 | 🟡 일부 |
| 4 | 캐싱 레이어 | ⭐⭐⭐ | 3 | ☐ |
| 5 | 전종목 조회 | ⭐⭐⭐ | 3,4 | 🟡 일부 |
| 6 | 입출금 레이더 🔑 | ⭐⭐⭐ | 2 | ☐ |
| 7 | WebSocket 수집기 | ⭐⭐⭐⭐ | 5 | ☐ |
| 8 | 수집 상태 | ⭐⭐ | 7 | ☐ |
| 9 | 선물 갭 · 선선갭 | ⭐⭐⭐⭐ | 7 | ☐ |
| 10 | 기록/통계 (DB) | ⭐⭐⭐⭐⭐ | 7 | ☐ |

> **1~5단계를 끝내면 메인 화면(실시간 스프레드 탭)이 동작한다.** 여기까지는 기존 구조를 크게 바꾸지 않는다.
> **6단계는 의존이 적어 병렬 진행이 가능**하지만 API 키 발급이 선행되어야 한다.
> **7단계부터가 전환점** — "요청 시 조회"에서 "상시 수집"으로 구조가 바뀐다.

## 4단계 — 캐싱 레이어 ⭐⭐⭐

176페어를 지금 구조로 돌리면 **업비트 초당 10회 제한 때문에 한 바퀴에 18초**가 걸린다.
캐싱 없이는 전종목 화면이 성립하지 않는다.

- [ ] 캐시 추상화 설계 (인메모리 우선, 나중에 Redis 교체 가능하게)
- [ ] 호가 캐시 — 키 `(거래소, 심볼, 시장구분, depth)`, TTL 0.5~2초
- [ ] 마지막 체결가 캐시 — 동일 구조
- [ ] **동시 요청 병합(single-flight)** — 같은 키에 몰리면 실제 호출 1회
- [ ] 캐시 히트/미스 지표 노출
- [ ] `depth` 가 다른 요청 처리 — 큰 depth 결과를 잘라 재사용
- [ ] 테스트: TTL 만료, single-flight 동작

### 완료 기준

- [ ] 동일 심볼 초당 100회 호출 시 거래소 호출이 초당 1~2회 이하
- [ ] 기존 테스트 97개가 그대로 통과

> **주의**: TTL 을 너무 늘리면 국내·해외 조회 시각이 벌어져 **프리미엄이 틀어진다.**
> 1초 이하 권장.

## 7단계 — WebSocket 실시간 수집기 ⭐⭐⭐⭐

목업 좌상단 `● 실시간 수집 중` 과 초 단위 갱신. **아키텍처 전환점.**

```
[지금]  요청 → REST 호출 → 응답        (매번 수십 ms)
[목표]  수집기 ← WS 푸시 ← 거래소
        요청 → 메모리 조회 → 응답       (1ms 미만)
```

### 7-1. 스트리밍 인터페이스

- [ ] 바이낸스 `wss://stream.binance.com:9443/ws/{symbol}@depth10@100ms` 구현
- [ ] 나머지 6개 거래소 순차 구현

### 7-2. 수집기

- [ ] 백그라운드 수집 태스크 — 앱 `lifespan` 에 연결
- [ ] 인메모리 스토어 (심볼별 최신 호가/체결가 + 수신 시각)
- [ ] 구독 관리 — 추적 페어 목록(3단계) 기준으로 구독
- [ ] **재연결 · 지수 백오프 · 구독 재등록**
- [ ] **바이낸스 depth 스냅샷 + 델타 동기화** (정확도의 핵심)
- [ ] REST 폴백 — WS 끊기면 자동 전환
- [ ] 메모리 상한 관리

### 7-3. 서비스 연동

- [ ] `market_data_service` 가 캐시 대신 스토어를 읽도록
- [ ] 스토어에 없으면 REST 로 폴백
- [ ] 데이터 신선도(`age_ms`) 응답에 노출

### 완료 기준

- [ ] API 응답 시간 수십 ms → **1ms 미만**
- [ ] rate limit 소모가 사실상 0
- [ ] 연결을 강제로 끊어도 자동 복구된다
- [ ] 24시간 연속 구동 시 메모리 누수 없음

> **주의**: 가장 어려운 단계다. **여러 프로세스로 띄우면 각자 연결을 잡으므로**
> 수집기를 별도 프로세스로 분리하는 설계를 먼저 검토할 것.

## 8단계 — 수집 상태 API ⭐⭐

- [ ] 실제로 한 거래소 연결을 끊으면 상태가 바뀐다

## 9단계 — 선물–현물 갭 · 선선갭 ⭐⭐⭐⭐

탭 2개. **선물 도메인 지식이 추가로 필요하다.**

### 9-1. 선물–현물 갭 (베이시스)

- [ ] `GET /futures/basis` — 무기한 선물 vs 현물 가격차
- [ ] **펀딩비 조회** — `GET /fapi/v1/premiumIndex`
- [ ] 김프와 결합 — 국내 현물 매수 + 해외 선물 숏 (헤지 진입)
- [ ] 거래소별 선물 지원 여부 확인

### 9-2. 선선갭 (캘린더 스프레드)

- [ ] **분기 선물(quarterly) 지원** — 지금은 무기한만
- [ ] 심볼 체계 확장 (`BTCUSDT_240628` 형태)
- [ ] `GET /futures/calendar-spread` — 만기물 간 가격차
- [ ] 만기일 정보 조회

> **주의**: 선물 rate limit 이 현물의 **절반 이하**(2,400/분)라 더 빡빡하다.
> 업비트에는 선물이 없으므로 국내 쪽은 항상 현물이다.

## 10단계 — 기록/통계 (DB) ⭐⭐⭐⭐⭐

`기록/통계` 탭. 지금까지는 전부 실시간 조회라 저장소가 없었다.

- [ ] 시계열 DB 선정 (TimescaleDB / InfluxDB / ClickHouse)
- [ ] 스키마 설계 — 페어 × 시각 × 프리미엄
- [ ] 수집기가 주기적으로 스냅샷 적재
- [ ] **보존 정책** — 176페어 × 1초 = 하루 1,500만 행
- [ ] 다운샘플링 (1초 원본 → 1분/1시간 집계)
- [ ] `GET /history/premium` — 기간별 추이
- [ ] 통계 — 평균/최대/최소 김프, 임계 초과 빈도, 시간대별 패턴
- [ ] 백업 · 마이그레이션 절차 문서화

> **주의**: **운영 부담이 실제로 생기는 첫 단계다.** 앞 단계들과 달리
> "코드만 짜면 되는" 일이 아니다.
