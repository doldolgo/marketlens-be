# MarketLens DB 구조

테이블 7개를 세 그룹으로 나눠 설명한다. 모든 예시는 실제 저장된 데이터다.

```
그룹 A. 라이브 (지금 이 순간)      — POST /refresh 가 매번 통째로 갱신
  market_snapshots   거래소×코인별 현재가·호가·입출금 상태
  fx_rate            통일 환율 (하나은행 고시 USD/KRW) — 항상 1행

그룹 B. 변동 이력 (김프/역프 통계의 재료) — POST /history/sync 가 쌓아감
  price_points       오늘치 가격 변동 이벤트 (압축 전 스테이징)
  price_chunks       완결된 하루치 압축 청크 (본 저장소)
  fx_points          오늘치 환율 변동 이벤트
  fx_chunks          환율의 하루치 압축 청크
  history_cursors    시리즈별 "어디까지 수집했나" 책갈피
```

데이터 흐름 한눈에:

```
/refresh  ──▶ market_snapshots + fx_rate           (덮어쓰기 — 과거 안 남음)
/history/sync ─▶ price_points·fx_points 에 변동 적재 ──자정 지나면──▶ *_chunks 로 압축
GET /history/* ─▶ chunks(과거) + points(오늘) 를 합쳐 변동 로그로 반환
```

## 공통 규칙 — 시각과 단위

- **시각은 epoch 초**(BIGINT)로 저장한다. `1786634103` 같은 숫자지만 **연도까지
  담긴 완전한 시각**이다 (= 2026-08-14 00:15:03 KST). 상대 시간("몇 초 뒤")은
  저장하지 않고 조회 API 가 계산한다.
- 사람이 읽을 때는 **읽기 전용 뷰**를 쓴다 — `v_price_points`, `v_price_chunks`
  등 (아래 [읽기 뷰](#읽기-뷰) 참고). 연도 포함 KST 시각과 실제 단위 가격으로
  풀어서 보여준다.
- **가격 단위는 `exchange` 컬럼이 결정한다** — `upbit` 행은 KRW, `binance`
  행은 USDT, 환율(`fx_*`)은 USD 1달러당 원. 별도 단위 컬럼은 두지 않는다
  (행마다 중복이라서). API 응답에는 `quote` 필드로 나간다.
- 스테이징의 가격은 **십진 문자열**이다 — float 반올림을 원천 차단해 무손실을
  보장하기 위해서다. 산술은 Decimal 로 한다.

## 그룹 A. 라이브 테이블

### `market_snapshots` — 거래소×코인별 현재 시세 스냅샷

거래소 하나 × 코인 하나당 **딱 한 행**. `POST /refresh` 가 매번 UPSERT 하고
상장폐지 코인은 지운다. 김프·슬리피지·차익 등 모든 라이브 계산의 재료.
과거는 남지 않는다 — 그래서 그룹 B 가 따로 있다.

| 컬럼 | 의미 |
|---|---|
| `exchange`, `base` (PK) | 거래소 ID(upbit/bithumb/binance) + 코인 심볼(BTC) |
| `native_symbol` | 거래소 원본 표기 (`KRW-BTC` / `BTCUSDT`) |
| `quote` | 가격 통화 (KRW 또는 USDT) |
| `price` | 마지막 체결가 (quote 통화 그대로) |
| `asks` / `bids` | 호가창 JSON `[[가격, 잔량], ...]` — 10억원 체결 커버 깊이까지 |
| `deposit_enabled` / `withdrawal_enabled` | 입금/출금 가능 여부 (API 키 없으면 null) |
| `price_timestamp` | 거래소가 준 시세 시각 (epoch **ms**) |
| `updated_at` | DB 저장 시각 — 신선도 판단 기준 |

예시 행: `(binance, BTC, BTCUSDT, USDT, 63747.2, asks=[[63745.61, 7.686], ...])`

### `fx_rate` — 통일 환율, 항상 딱 1행

모든 원화 환산이 쓰는 **단 하나의 환율** — 하나은행 고시 매매기준율.
refresh/sync 가 최신 고시로 계속 덮어쓴다 (더 오래된 고시로의 역행은 UPSERT
의 WHERE 절이 막는다). 과거 환율은 `fx_chunks`/`fx_points` 에 쌓인다.

| 컬럼 | 의미 |
|---|---|
| `id` (PK) | 항상 1 — 단일 행 강제 |
| `rate` | USD 1달러당 원화 (매매기준율) |
| `source_time` | **은행이 고시한** 시각 (epoch 초) |
| `round_no` | 당일 고시 회차 (하루 1,300~2,000회) |
| `updated_at` | DB 저장 시각 |

예시 행: `(1, 1418.0, 1786634083, 872)` — "오늘 872번째 고시, 1,418원".

> 예전의 거래소별 KRW-USDT 환율 테이블(`krw_rates`)은 폐기됐다.
> 남아 있다면 `DROP TABLE krw_rates;` 로 지운다 ([DEPLOY.md](DEPLOY.md) 참고).

## 그룹 B. 변동 이력 테이블

핵심 설계 두 가지:

1. **가격이 변한 순간만 저장한다.** 같은 가격이 이어지는 구간은 "안 변했다"는
   정보뿐이라 버려도 손실이 아니다. 덕분에 바이낸스는 하루 86,400초가
   3~4만 건으로, 업비트는 체결 초의 절반 이하로 준다.
2. **오늘치는 읽기 쉬운 행으로, 완결된 하루는 압축 청크로.** 자정(UTC)이
   지나면 `*_points` 의 그 날 행들이 `*_chunks` 한 행으로 압축되고 스테이징은
   비워진다.

### `price_points` — 코인 가격 변동 이벤트 (오늘치 스테이징)

| 컬럼 | 의미 |
|---|---|
| `exchange`, `base`, `ts` (PK) | 거래소 + 코인 + **변동 시각 (epoch 초)** |
| `price` | 변동 후 가격 — 십진 문자열. **단위: upbit=KRW, binance=USDT** |

예시 행: `(binance, BTC, 1786634103, "63824.02000000")`
→ "2026-08-14 00:15:03 KST 에 가격이 63,824.02 USDT 가 됐다".
인접 행과 가격이 반드시 다르다 (변동만 저장).

### `price_chunks` — 완결된 하루치 압축 청크 (본 저장소)

(거래소 × 코인 × UTC 날짜)당 한 행. `data` 에 그 날의 (시각, 가격) 열 전체가
압축돼 있고, 나머지 컬럼은 blob 을 풀지 않고 쓰는 요약값이다.

| 컬럼 | 의미 |
|---|---|
| `exchange`, `base`, `day` (PK) | 거래소 + 코인 + UTC 날짜 |
| `codec` | 압축 포맷 버전 (현재 1) — 포맷이 바뀌어도 옛 청크를 읽기 위함 |
| `price_scale` | 가격 = 정수 ÷ 10^scale (예: scale=2 → 6359400 = 63,594.00) |
| `n_points` | 담긴 변동 이벤트 수 |
| `first_ts` / `last_ts` | 그 날 첫/마지막 변동 시각 (epoch 초) |
| `first/last/min/max_price` | 시·종·저·고가 (스케일 정수) |
| `data` | 압축 바이너리 — 100% 복원 가능 (아래 검증 참고) |

예시 행: `(binance, BTC, 2026-08-12, n_points=36152, scale=2, data=34KB)`
— 하루 36,152건의 변동이 34,020바이트, **건당 0.94바이트**.

### `fx_points` / `fx_chunks` — 환율의 같은 구조

환율은 거래소·코인 개념이 없어 키가 시각/날짜뿐이다.
`fx_points`: `(ts PK, price)` — 단위: USD 1달러당 원.
`fx_chunks`: `price_chunks` 와 동일 구조에서 `exchange`/`base` 만 없다.

예시: `fx_chunks (2026-08-12, n_points=5, scale=1, data=34바이트)` — 그 날
환율 변동 5건 (1,417.1 → 1,419.0).

### `history_cursors` — 증분 수집 책갈피

sync 가 매분 돌 때 같은 구간을 다시 받지 않게 하는 장치.

| 컬럼 | 의미 |
|---|---|
| `exchange`, `base` (PK) | 시리즈 식별자. 환율은 고정 키 `(fx, USD)` |
| `last_ts` | 마지막으로 **관측한** 시각 — 다음 sync 는 그 다음 초부터 |
| `last_price` | 마지막 관측 가격 — "변했나" 판정의 비교 기준(씨앗) |

커서는 DB 차원에서 역행이 막혀 있다 (UPSERT 의 WHERE 절) — refresh 와 sync
가 동시에 돌아도 과거로 되돌아가지 않는다.

## 압축은 어떻게 되고, 정말 복원되나

### 원리 — 차이만 저장한다

절대값(1786504303, 14171)은 크지만 **이웃과의 차이는 작다.** 시각은 간격,
가격은 변화량만 저장하면 1~3바이트씩이면 되고, 순서대로 더하면 원본이
정확히 복원된다. 정보를 버리는 압축이 아니라 **표현만 바꾸는** 압축이라
100% 가역이다. 4단계: ① 가격을 스케일 정수로 (float 안 거침) → ② 델타화 →
③ varint (작은 수 = 짧은 바이트) → ④ zstd. 구현: `app/history/codec.py`.

실물 예 — 환율 하루치(변동 5건) 청크의 압축 풀린 payload 는 **25바이트**다:

```
01 05 | efc8efd306 | ce8101 be8301 9236 d39201 | b6dd01 | 0c 03 23 42
버전  n=5  첫 시각      시간 간격 4개(+16590s...)   첫 가격    가격 변화(+0.6,-0.2,-1.8,+3.3)
```

### 검증 — 실데이터로 확인된 사실 (2026-08-14)

1. **쓰기 시 자동 검증**: 저장 경로는 `encode_points_verified()` 를 지난다 —
   인코딩 직후 다시 디코딩해 원본과 대조하고, 다르면 저장 전에 예외.
2. **원본 대조 검증**: DB 의 8/12 바이낸스 청크(34KB)를 복호화한 36,152건을,
   같은 날 데이터를 바이낸스에서 **새로 받아온 원본**과 1건씩 전부 비교 —
   시각·가격 **36,152건 전부 일치, 불일치 0건**. 환율 청크도 하나은행 재조회
   원본과 6건 전부 일치.
3. 실측 압축률: 일반 DB 행(~72 B/건) 대비 **약 80~180배** (0.4~0.94 B/건).
   BTC 3개월 전체(업비트+바이낸스+환율)가 7MB 미만.

## 읽기 뷰

epoch 초·스케일 정수는 사람이 못 읽으므로, 앱 기동 시 읽기 전용 뷰를 만든다
(`app/db/views.py`, PostgreSQL 전용). GUI 뷰어에서는 이 뷰를 열면 된다.

| 뷰 | 보여주는 것 |
|---|---|
| `v_price_points` | 변동 이벤트 — `time_kst` (연도 포함 KST) + 가격 |
| `v_fx_points` | 환율 이벤트 — `time_kst` + 환율 |
| `v_price_chunks` | 청크 요약 — 시각·시/종/저/고가를 실제 단위로 |
| `v_fx_chunks` | 환율 청크 요약 |
| `v_history_cursors` | 커서 — 마지막 수집 시각(KST) |
| `v_fx_rate` | 라이브 환율 + 고시 시각(KST) |

예시 (`SELECT * FROM v_fx_chunks`):

```
    day     | n_points |   first_time_kst    | open_rate | close_rate | blob_bytes
------------+----------+---------------------+-----------+------------+-----------
 2026-08-12 |        5 | 2026-08-12 12:11:43 |    1417.1 |     1419.0 |         34
```

## 접속 방법

- **로컬**: `docker compose -f docker-compose.dev.yml up -d` 후
  `127.0.0.1:5432`, 계정/비밀번호/DB 모두 `marketlens`.
  웹 뷰어 Adminer: http://localhost:8080 (서버 `db`).
- **운영(RDS)**: 퍼블릭 액세스가 없어 EC2 경유 SSH 터널로 접속한다
  (DBeaver/Beekeeper 의 SSH 탭 — Host 는 EC2, DB 는 RDS 엔드포인트).
- 테이블·뷰는 앱 기동 시 자동 생성된다 (별도 마이그레이션 없음).
